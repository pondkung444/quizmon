## 2. หลักการออกแบบที่ยึดตลอด (ไม่เคยเปลี่ยนตั้งแต่ v3)

1. **ไม่ลงโทษรุนแรง** — ตอบผิดได้ ไม่หักคะแนน สัตว์ไม่ตาย ลบไม่ได้ ไม่มีความหิว · **ไม่มีการสุ่มที่
   ทำให้ผู้เล่นเสียของหรือถอยหลัง** และของสำคัญที่ต้องสุ่ม (ไข่ rare/epic, คุณภาพอุปกรณ์) มีระบบ
   การันตีรองรับเสมอ (pity meter — ดู §4.11/§4.12) เกมมีองค์ประกอบสุ่มจริง (ดรอปไข่, สุ่มคำถาม,
   สุ่มค่าอุปกรณ์) แต่ไม่มีกรณีไหนที่สุ่มแล้วผู้เล่น "แพ้/เสียของที่มีอยู่แล้ว" จากดวงล้วนๆ
2. **ให้คุณค่าความพยายามพอๆ กับความเก่ง** — ตัวคูณแม่นยำมีพื้นล่าง ×0.8
3. **ทุกคนมีที่ยืน** — บุคลิกเลือกเองได้ ทำให้เก็บสมุดครบ 12 ช่องได้จริง
4. **ความหายาก = สวย/ภูมิใจ ไม่ใช่แรงกว่า** — ไข่ legendary caps เท่ากันหมด 100 ไม่ได้เปรียบในเกม
5. **การเรียนคือแกน** — EXP และวิวัฒนาการต้องมาจากตอบคำถามเสมอ (Qmon AI **ห้าม** ให้ EXP)
6. **derive ดีกว่าเก็บซ้ำ** — แต่แยกให้ออก: counter เสี่ยง race → ต้อง atomic RPC ·
   event ที่เกิดครั้งเดียว → เก็บเป็น log ปลอดภัยกว่าสร้าง snapshot table
7. **feedback เชิงบวกทั้งหมด** — ไม่มีข้อความเชิงลบใน UI แม้แต่จุดเดียว
8. **Qmon เชียร์เพราะเด็กเก่งขึ้น ไม่ใช่เด็กทำเพราะกลัว Qmon เสียใจ** — ห้าม AI ใช้ความรู้สึก
   ของตัวละครเป็นแรงกดดัน (ได้ engagement ระยะสั้น แต่ครูไม่ควรสร้าง)

## 3. ระบบแกน (core progression)

### 3.1 EXP

```
EXP ต่อข้อ = base × ตัวคูณแม่นยำ × ตัวคูณคอมโบ
base = 10 (โหมดปกติ) / 12 (โหมดติวกลางภาค)
soft cap = 180 EXP ต่อวัน (Bangkok day)
```
ไฟล์: `src/lib/exp.ts` — **ไฟล์ protected ห้ามแก้เด็ดขาด** (import ใช้ได้อย่างเดียว)

### 3.2 วิวัฒนาการ

- persisted 4 stage ที่ใช้จริง · CHECK ใน DB รับถึง 5 แต่ **ไม่มีเนื้อหา/รูปของ stage 5**
- threshold: `{1→2: 50, 2→3: 350, 3→4: 900}` · ขยับได้ทีละ 1 stage ต่อรอบ
- จุดเขียนจริงจุดเดียว: `finishQuizRound()` ใน `src/app/quiz/actions.ts`
- ไฟล์: `src/lib/evolution.ts` — **protected** (ยกเว้น `computeRawStats()` ที่เคยยกเว้นให้ครั้งเดียว)

> **ประเด็น game design ที่ยังเปิดอยู่:** stage 4 คือเพดานจริงในทางปฏิบัติ และเป็นจุดที่
> ทุกอย่าง (บุคลิก + สเตตัส 5 ค่า) เปิดเผยพร้อมกัน ซึ่งดันเป็นจุดที่เด็กมักหยุดเล่นพอดี — ตอนนี้มี
> pet stage 4 แล้ว **78 ตัวจาก 194 (40%)** ตอนนี้มีผจญภัย/ท้าทาย/achievement มารองรับหลัง stage 4
> แล้ว (ดู §4.11-§4.13) แต่ยังไม่มีข้อมูล retention พอจะสรุปว่าช่วยได้แค่ไหน (ดู §7.1)

### 3.3 สาย (subline) — 6 ค่าใน DB, แยกตาม band

`pets.subline` CHECK ปัจจุบัน (ยืนยันจาก production):
`NULL | math | science | balanced | physics | chemistry | biology`

**junior** — ล็อกตอน stage 3 จากสัดส่วนข้อที่ตอบถูก ≥60%

| subline | ป้ายไทย | ตัวคูณสเตตัส |
|---|---|---|
| `math` | สายคณิต | ATK 1.3 · FOC 1.3 · HP 0.9 · DEF 0.9 |
| `science` | สายวิทย์ | HP 1.3 · DEF 1.3 · ATK 0.9 · FOC 0.9 |
| `balanced` | สายสมดุล | ทุกค่า 1.0 · SPD 1.1 |

**senior** — ล็อกตอน stage 3 จาก "สายที่ตอบถูกมากที่สุด" (เสมอ = สุ่ม, ไม่มีขั้นต่ำ)
นับผ่าน RPC `get_pet_branch_counts(pet_id)` ที่ join `questions.branch`

| subline | ป้ายไทย | เลนศิลป์/สเตตัสที่ map ไป (`artLane`) |
|---|---|---|
| `physics` | สายฟิสิกส์ | → `math` (ATK/FOC เด่น) |
| `chemistry` | สายเคมี | → `balanced` (สมดุล + SPD) |
| `biology` | สายชีวะ | → `science` (HP/DEF เด่น) |

**กฎเหล็กของสถาปัตยกรรมนี้ (Option C):**
ค่าที่ไหลเข้า `evolution.ts` **ต้องผ่าน `artLane()` ก่อนเสมอ** ·
ค่าที่ไหลออกไปหาผู้ใช้ (ป้ายไทย/บทพูด) **ต้องไม่ผ่าน `artLane()`**
→ ทำให้ไม่ต้องแตะไฟล์ protected และไม่ต้องวาดรูปใหม่ 18 ไฟล์
ไฟล์แกน: `src/lib/petLine.ts`

### 3.4 บุคลิก (personality) — A/B

- `pets.personality` = `A` (ดุดัน) หรือ `B` (สุขุม) · ล็อก **ตอน stage 4 เท่านั้น** · ถาวร
- ตัดสินจาก **majority vote ของอาหาร A/B ที่ป้อนสะสม** (`pet_feedings`) · เสมอ → สุ่มคำถาม
  1 ใน 4 ให้ผู้เล่นเลือกเอง
- ผลต่อเกม: ตัวคูณสเตตัส **+5% เฉพาะ 2 ค่า ไม่ใช่ทุกค่า** — ไม่มีผลต่อบับเบิลคำพูด
  | บุคลิก | ได้ +5% ที่ | ค่าที่เหลือ |
  |---|---|---|
  | `A` (ดุดัน) | **ATK · SPD** | ×1.0 |
  | `B` (สุขุม) | **HP · DEF** | ×1.0 |

  ที่มา: `PERSONALITY_BONUS` ใน `src/lib/evolution.ts` (verify กับซอร์สจริง 5 ส.ค. 2026)
  ⚠️ v7 ฉบับก่อนเขียนว่า "+5% เท่านั้น" ซึ่งตีความผิดเป็น "ทุกค่า" ได้ — เคยทำให้คำนวณ DEF
  ผิด +3 มาแล้ว ดู `stat-formula-VERIFIED-2026-08-05.md`

  > ผลข้างเคียงที่รู้แล้ว: บุคลิกมาจากโหวตอาหารซึ่งไม่เกี่ยวกับ subline → เด็กราวครึ่งหนึ่ง
  > (14/25 pet stage 4 ที่ไม่ใช่สายสมดุล) ได้ +5% ลงบนสเตตัสที่อ่อนที่สุดของตัวเอง
  > เช่นสายวิทย์ที่ได้บุคลิก A → บวก ATK ที่เกือบเป็นศูนย์ · ยังไม่ถือเป็นบั๊ก แต่แปลว่า
  > บุคลิกแทบไม่มีผลจริงกับครึ่งหนึ่งของผู้เล่น
- เขียน DB จุดเดียว: `choosePersonalityAfterEvolve()` ใน `src/app/pet/actions.ts`
  (guard ด้วย `.is("personality", null)`)

> ⚠️ **สับสนง่ายที่สุดในโปรเจกต์:** มี "บุคลิก" 2 ระบบคนละเรื่อง —

> กับ `pets.personality` (DB: A/B ใช้คูณสเตตัส) **ไม่เกี่ยวกันเลย**

### 3.5 สเตตัส 5 ค่า — snapshot ตอน stage 4

| สเตตัส | raw มาจาก |
|---|---|
| **HP** | `science_correct` สะสม |
| **ATK** | `math_correct` สะสม |
| **DEF** | `min(math_correct, science_correct) × 2` |
| **FOC** | ความแม่นยำเฉลี่ย (0-100) |
| **SPD** | `combo_milestones` (นับทุกครั้งที่ streak แตะจุดคูณของ 3) |

pipeline: `computeRawStats()` → ตัวคูณ subline → **บุคลิก +5% เฉพาะ 2 ค่า (ดู 3.4)** →
egg curve (`rate_multiplier`/`base_offset`) → `Math.round()` **ครั้งเดียวท้ายสุด** → clamp cap ของไข่

**สเตตัสถูกใช้จริงในระบบท้าทาย** (ไม่ใช่แค่โชว์ radar เฉยๆ) — ด่านอุปสรรค: โอกาสผ่านด้วยพลังตัวเอง
= `stat ÷ cap` แปลงเป็นสี (≥60% เขียว/≥35% เหลือง/ต่ำกว่าแดง) · บอส: ผลรวม 5 ค่า ÷ 500 เทียบ
threshold ของด่าน (45%/60%/75%) — ดู §4.12

**ตรวจสอบความถูกต้องของสูตร (5 ส.ค. 2026):** audit pet stage 4 ทั้ง 31 ตัวใน production ตอนนั้น →
ตรงเป๊ะ 29/31 อีก 2 ตัวต่างที่ SPD แบบ `db < calc` เพราะ `combo_milestones` โตต่อหลัง snapshot (ปกติ
ไม่ใช่บั๊ก) ไม่พบเคส `db > calc` เลย → **สูตรคำนวณถูกต้อง ไม่มีบั๊ก**

> คุยกันเมื่อ 15 ส.ค. 2026 หลังพบว่า raw stat ของ senior ปัจจุบัน "เคมี" กับ "ชีวะ" ใช้
> ข้อมูลกองเดียวกัน (`science_correct`) แยกไม่ออกจริง (ดูหมวด 3.5 ด้านบน + `subline` ตัวอย่างจริง
> จาก DB: pet subline=biology 9 ตัว มี `science_correct` 62-183 ปนกันหมด ไม่รู้ว่าตอบเคมีหรือชีวะ)

**ไอเดีย:** ผูกแต่ละวิชาตรงกับสเตตัสเป็น 1:1 แทน `min()` เดิม เช่น ฟิสิกส์→ATK ตรงตัว ·
**เคมี→DEF ตรงตัว** · ชีวะ→HP ตรงตัว — แก้ปัญหาเดิมของ v7 §7.5 ที่เคยปัดตกไอเดียนี้เพราะ

เคมีแทน `min()`** — อาจจะเป็นสูตรที่ดีกว่าของเดิมด้วยซ้ำ

**ถ้าจะทำจริง ไม่ใช่ patch เล็ก — ต้องรื้อสถาปัตยกรรมสเตตัส senior บางส่วน:**
1. ต้องมีแหล่งข้อมูลนับแยกเคมี/ชีวะ/ฟิสิกส์ถาวร — เพิ่มคอลัมน์ใหม่ใน `pets` (ต้องแก้ `submitAnswer()`)

2. `computeRawStats()` ต้องมี path แยกสำหรับ senior (เป็นข้อยกเว้นที่อนุมัติแล้วของไฟล์ protected
   แก้ได้โดยไม่ผิดกฎ — แต่ junior ต้องไม่ถูกแตะ)
3. ต้องตัดสินใจใหม่ว่า FOC/SPD จะแยกตามวิชาด้วยไหม หรือยังใช้ร่วมกันทั้ง 3 สายเหมือนเดิม
4. `SUBLINE_MULTIPLIER` ของ senior (ตอนนี้เป็น winner-take-all ผ่าน `artLane()`) ต้องนิยามใหม่ทั้งชุด
   ไม่ใช่ปรับตัวเลข
5. สถาปัตยกรรม Option C (`artLane()`, v7 §3.3) ออกแบบมาเพื่อ "ไม่ต้องแตะ protected + ไม่ต้อง

### 3.5.2 ✅ จูนสูตร FOC/SPD — ตัดสินใจแล้ว รอ implement เป็น v1.0.1 (ยังไม่ใช่ v1.0)

> **สถานะ: เคาะแล้ว เลือก "แบบ B" · ยังไม่ implement · จะเป็น v1.0.1 เมื่อขึ้น production**
> สูตรที่ยัง**ใช้งานจริงใน v1.0 ตอนนี้** คือของเดิม (ดู §3.5 ด้านบน: FOC = ความแม่นยำตรงๆ, SPD =
> `combo_milestones` ตรงๆ) — เนื้อหาด้านล่างคือ**แผนของ v1.0.1** บันทึกไว้ล่วงหน้าเพื่อไม่ให้หลุด
> ต่างจาก §3.5.1 (แยกสูตร senior) ที่พักไว้ไม่ทำเลย — อันนี้ตัดสินใจว่าจะทำแน่นอน แค่ยังไม่ถึงคิว

**ปัญหาที่แก้:** FOC ตันคงที่ 85% ของทุกคน (แยกแยะฝีมือไม่ได้) · SPD เฉลี่ย 31% ไม่มีใครถึง cap เลย
→ ทั้ง 2 แกน "ตาย" ในเชิงเกม และทำให้ radar หน้าโปรไฟล์เบี้ยวไม่สวย (ซึ่งเป็นจุดตั้งต้นที่ปอนด์สังเกตเห็น)

**สูตรใหม่ — แก้ 2 บรรทัดใน `computeRawStats()` เท่านั้น:**

```
FOC: ค่าดิบ = ความแม่นยำ × 0.7      (เดิม: ความแม่นยำ ตรงๆ)
SPD: ค่าดิบ = combo_milestones × 2   (เดิม: combo_milestones ตรงๆ)
```

**ผลจำลองกับ pet stage 4 จริงทั้ง 78 ตัว:**

| แกน | เดิม (เฉลี่ย %cap) | ใหม่ | เขียว/เหลือง/แดง เดิม → ใหม่ |
|---|---|---|---|
| FOC | 85% | **60%** | 70/8/0 → **47/30/1** |
| SPD | 31% (32% รวมอุปกรณ์) | **55%** (56% รวมอุปกรณ์) | 1/22/55 → **28/44/6** |

**เหตุผลที่เลือกแบบ B (×0.7) แทนแบบ A (หักพื้น 30 แล้วขยาย):**

| | ผลรวมเฉลี่ย | ผ่านด่าน 1 | ผ่านด่าน 2 | ผ่านด่าน 3 |
|---|---|---|---|---|
| ตอนนี้ | 56% | 56 คน | 31 คน | 4 คน |
| **แบบ B (เลือก)** | **56%** ✅ | 54 | 34 | **4** ✅ |
| แบบ A | 58% | 57 | 36 | 9 (ง่ายขึ้นเท่าตัว) |

→ **แบบ B รักษาสมดุลระบบท้าทายไว้ได้เป๊ะ ไม่ต้องแตะอะไรเพิ่มเลย:** ไม่ต้องแก้ threshold บอส 45/60/75 ·
ไม่ต้องแก้งบอุปกรณ์ 75 แต้ม · ไม่ต้องแก้ cap ไข่ · ไม่ต้องแตะ RPC ของ raid สักตัว
(FOC ลด ~25 จุด กับ SPD เพิ่ม ~24 จุด หักล้างกันพอดี)

**ประเด็นอุปกรณ์ที่ต้องรู้ (ปอนด์เป็นคนชี้จุดนี้):** อุปกรณ์มีแค่ 4 แกน ATK/HP/DEF/SPD **ไม่มี FOC**
→ SPD ได้ทั้งสูตรใหม่ + อุปกรณ์ช่วย (double-dip เล็กน้อย, เฉลี่ยอุปกรณ์ให้ +9.9 แต้ม) ส่วน FOC ลดลง
โดยไม่มีทางชดเชยเลย · ยอมรับได้ในแบบ B เพราะ FOC ยังอยู่ที่ 60% (สูงเป็นอันดับ 2 รองจาก DEF)
ไม่ได้กลายเป็นแกนที่แย่ที่สุด — ต่างจากถ้าลดแรงกว่านี้

**สิ่งที่แบบ B ไม่ได้แก้ (ยอมรับแล้ว):** การคูณ 0.7 ย่อสเกลลงทั้งแถบ ไม่ได้กางความต่างระหว่างเด็กแม่นมาก
กับแม่นน้อยให้ชัดขึ้น (ค่าดิบยังกระจุกแคบเหมือนเดิม) · radar ที่ยังเอียงหลังแก้ มาจาก 2 เหตุที่ไม่เกี่ยวกับ
สูตรนี้: (1) เด็กที่เล่นน้อย HP/ATK ต่ำจริงตามเจตนาเกม (2) `DEF = min(math,science)×2` ตัวคูณ 2 ทำให้
DEF เด่นกว่าแกนอื่นเชิงโครงสร้าง + cap ต่อแกนของไข่แต่ละใบต่างกันโดยตั้งใจ (คาแรกเตอร์ไข่)

**เรื่องที่ต้องตัดสินใจตอน implement: pet 78 ตัวเดิมเก็บ stat เป็น snapshot ถาวร** สูตรใหม่มีผลเฉพาะตัวที่
ถึง stage 4 หลังจากนี้ → ถ้าไม่ backfill ปัญหา radar เบี้ยวยังอยู่กับเด็กทั้ง 78 คนที่มีอยู่
(Claude แนะนำให้ backfill · ปอนด์ยังไม่เคาะ — อยู่ใน handoff)

## 4. ฟีเจอร์ทั้งหมดที่ใช้งานจริงตอนนี้

### 4.1 ทำโจทย์ + ภารกิจรายวัน

- อัตราจบภารกิจเมื่อเริ่มแล้ว: 89% (ข้อมูล ก.ค.)

### 4.2 ปุ่มเลือกฝึกแยกสาย
- **junior**: คณิต / วิทย์ (filter ด้วย `questions.subject`)
- **senior**: ฟิสิกส์ / เคมี / ชีวะ (filter ด้วย `questions.branch`)
- ⚠️ เป็น **presentation layer ล้วน** — กดปุ่ม "ฟิสิกส์" ยังวิ่งเข้า `math_correct` (ATK) ตาม
  mapping `subject` เดิม ไม่ได้เปลี่ยนตรรกะสเตตัส

- `player_food` (คลังต่อ user) · `pet_feedings` (log ทุกครั้ง) · RPC `feed_pet()`
- อาหารกำหนด **บุคลิก A/B** อย่างเดียว **ไม่เพิ่มพลัง ไม่มีความหิว**
- **แหล่งอาหารตอนนี้: ภารกิจรายวันเท่านั้น** — ผจญภัยเคยแจกอาหารด้วย แต่**ปอนด์ยืนยันแล้วว่าเปลี่ยน
  เป็นตั๋วท้าทายแทนโดยตั้งใจ** (ไม่ใช่ปิดชั่วคราว) ดู §4.11

### 4.7 Qmon พูดด้วย AI (Gemini) — ใช้งานจริงแล้ว

**สถาปัตยกรรม "คิดฝั่งเซิร์ฟเวอร์ พูดฝั่ง AI":** คำนวณสถิติเองจาก `quiz_attempts`

  `upsert_qmon_cache()` เท่านั้น (22 แถว)

**สัดส่วนการใช้จริง (50 ข้อความ):** gemini 22 / fallback 28

**ข้อห้ามที่ล็อกไว้ใน system prompt:** ห้ามให้ตัวเลขที่ไม่ได้ส่งใน payload · ห้ามสัญญารางวัล ·
ถ้า `data_confidence: low` ห้ามพูดถึงแนวโน้มเลย · **ห้ามพูดว่าคิดถึง/เหงา/เศร้าถ้าเด็กไม่เล่น**

**เหตุผลที่ยังไม่เปิดช่องพิมพ์อิสระ:** free tier รับ traffic สุ่มไม่ได้ · ความเสี่ยงกับเด็ก ม.ต้น

### 4.14 Profile & Friends (สังคม)

> Live ตั้งแต่ 14 ส.ค. 2026 · design doc ต้นฉบับ: `quizmon-profile-friends-system-design.md`

**Information architecture ตรงกับ design เป๊ะ:** เมนูล่างเปลี่ยนเป็น `บ้าน | สังคม | ฟาร์ม | หอเกียรติยศ`
(ไม่มีปุ่ม Profile แยก) · หน้า "สังคม" = route `/social` มี 3 แท็บ: **อันดับ | เพื่อน | โปรไฟล์**
(โค้ดจริงใช้ path ย่อย `/social`, `/social/friend/[id]`, `/social/profile/[id]`, `/social/requests`,
`/social/add-friend`, `/social/blocked`, `/social/encouragements` — ตรงกับ flow ที่ล็อกไว้)

**ระดับการมองเห็น 3 ชั้น (คนทั่วไป/เพื่อน/เจ้าของ) — ตรวจ RLS แล้วตรงกับตารางสิทธิ์ที่ล็อกไว้:**
โรงเรียน+ระดับชั้น+สถิติการฝึก+สเตตัส+Qmon ตัวโปรด แสดงเฉพาะเพื่อน/เจ้าของ, ชื่อ+Qmon ที่ภูมิใจ+
achievement ที่ปักหมุด 3 เหรียญ+จำนวนถูกใจ เห็นได้ทุกคน

**ระบบเพื่อน:** เพิ่มเพื่อนได้ 2 ทาง (Friend Code / เปิดจาก Leaderboard) ตรงกับ design —
`friend_code` มีครบทุกบัญชีแล้ว (126/126) ผ่าน `generate_friend_code()` · RPC ครบชุด
(`send_friend_request`/`respond_friend_request`/`cancel_friend_request`/`remove_friend`/
`_expire_stale_friend_requests`) · unfriend/block ทำงานแยกกัน (`blocks` คนละตารางกับ `friendships`)

**ส่งกำลังใจ (encouragements):** เลือกข้อความสำเร็จรูป 4 แบบ (`qmon_cool`/`good_job_today`/
`keep_going`/`reach_the_goal`) จำกัด **1 ครั้ง/วัน/คู่เพื่อน** — ยืนยันจาก DB constraint ตรงๆ
(`UNIQUE(sender_id, recipient_id, sent_date)`) ตรงกับ design เป๊ะ ไม่ใช่แค่ enforce ฝั่ง client

**อันดับ (ranking) — 4 หมวดตรงกับ design (Grid 2×2):** การฝึกประจำสัปดาห์ (คะแนนเดียวกับ weekly
leaderboard) · ความสม่ำเสมอ 30 วันล่าสุด (นับ + เช็ค streak) · Achievement (ให้แต้มตามระดับเหรียญ
Bronze1/Silver2/Gold3/Crown5) · นักสะสม Qmon (จำนวนรูปแบบ stage 4 ไม่ซ้ำที่ค้นพบ) · ขอบเขต "อันดับ
ทั้งหมด" แสดง Top 50 + การ์ดอันดับตัวเองถ้าไม่ติด Top 50 (ตรงกับ design), "อันดับเพื่อน" ไม่จำกัดจำนวน

**✅ อันดับ "ทั้งหมด" ไม่แยก junior/senior — ยืนยันเป็นการตัดสินใจตั้งใจจากปอนด์ (15 ส.ค. 2026):**
อันดับ "ทั้งหมด" (`scope='all'`) ไม่กรองด้วย `grade_band` เลย — ยืนยันจากซอร์ส `_ranking_candidates()`
จริง ต่างจาก Weekly Leaderboard เดิมที่แยก band เด็ดขาด **แต่เป็นความตั้งใจ ไม่ใช่บั๊ก**: ปอนด์ต้องการ
ให้ฟีเจอร์สังคมเป็นพื้นที่ที่ junior กับ senior มีโอกาสได้เจอกัน ต่างจาก Weekly Leaderboard ที่ยังคงแยก
กันเด็ดขาดเพราะเป็นการแข่งขันในกลุ่มเดียวกัน — สองระบบมีเป้าหมายต่างกันโดยเจตนา

**ตัวเลขจริง (15 ส.ค., เพิ่งเปิดมา ~1 วัน — แก้ไขจากที่เคยระบุผิด ดูหมายเหตุท้ายนี้):** เพื่อนยืนยันแล้ว
**4 คู่** · คำขอเพื่อนค้าง 1 + accepted 1 · ถูกใจ 1 ครั้ง · ส่งกำลังใจ 0 ครั้ง (ยังไม่มีใครใช้) · block 0 ครั้ง

**เพื่อน 4 คู่ที่มีจริง:** PonDKunG↔Dawu, ต้าอู๋ห์↔Dawu, PonDKunG↔ต้าอู๋ห์ (3 คู่แรกคือบัญชีทดสอบทั้ง 3
บัญชีเป็นเพื่อนกันครบเป็นสามเหลี่ยม น่าจะจากตอนทดสอบระบบ) + คุณ↔แพงๆ (คู่เดียวที่น่าจะเป็นนักเรียนจริง)

> ⚠️ **หมายเหตุความถูกต้อง (แก้ไข 15 ส.ค. 2026):** ตัวเลขชุดนี้ที่เคยใส่ไว้ตอนปิด Phase 5 ครั้งแรก
> ("3 คู่/คำขอค้าง 1/ถูกใจ 1/กำลังใจ 0/block 0") จริงๆ แล้วเป็นตัวเลขเก่าจาก `list_tables` ตอน Phase 1
> ไม่ใช่ query ใหม่ตอน Phase 5 จริง — เกิดจาก tool คืนผลแค่ query สุดท้ายเมื่อรันหลายคำสั่งรวมกัน
> ตรวจซ้ำแล้วแก้เป็นตัวเลขจริง ณ ตอนนี้ (ยืนยันทีละคำสั่งแยกกัน)

## 7. แผนในอนาคต

### 7.1 ลำดับความสำคัญสูงสุด — ปัญหา game design ที่ค้างมานาน

**(1) stage 4 คือกำแพง** — 78/194 ตัว (40%) ถึง stage 4 แล้ว และทุกอย่างเปิดเผยพร้อมกันตรงนั้น
(บุคลิก + สเตตัส 5 ค่า) ซึ่งดันเป็นจุดที่เด็กหยุดเล่น ตอนนี้มีผจญภัย/ท้าทาย/achievement มารองรับ
หลัง stage 4 แล้ว แต่ยังไม่มีข้อมูล retention พอจะสรุปว่าช่วยได้แค่ไหน

**ทิศทางระยะยาวที่เคาะแล้ว (15 ส.ค. 2026):** stage 5 และระบบ PvP **มีแผนเปิดทั้งคู่ แต่ไม่ใช่
เร็วๆ นี้** — ยังไม่มี timeline ชัดเจน รอดูข้อมูล retention จากระบบที่เพิ่งปล่อยก่อน

**(2) จอฉลอง stage 4 แยก** — ค้างมานาน · ตอนนี้ EXP + วิวัฒนาการ + personality modal
ยังกองรวมใน `QuizClient.tsx` เดียวกันหมด → จังหวะที่เด็กตื่นเต้นที่สุดของเกมยังไม่มีจอเฉพาะ

**(3) เปิดฟักซ้ำหลังเก็บสัตว์ทุกครั้ง** — ตอนนี้ปลดไข่ใบสองแค่ครั้งแรก (`first_pet_reward`)
→ คนที่เก็บครบแล้วไม่มีอะไรทำต่อ

### 7.2 วัดผลของที่เพิ่งปล่อย

- **Qmon AI fallback rate** — ลดลงจาก 56% → 31.7% แล้ว (ดู §8 #13) ยังไม่ทราบสาเหตุที่แท้จริงที่ทำให้ดีขึ้น
- **ไข่ legendary/Hall of Fame** — แจกไปแล้ว 1 ครั้ง ยังไม่รู้ผลต่อ retention
- **ยังไม่มี event วัดว่า Qmon AI ดันเด็กไปทำภารกิจจริงไหม** — ควรเพิ่ม
  `qmon_bubble_shown` / `qmon_bubble_to_mission` ถ้าไม่วัดจะไม่มีทางรู้ว่าคุ้มโควตาไหม
- **ระบบใหม่ 4 ระบบ (ผจญภัย/ท้าทาย/achievement/สังคม)** — ยังใหม่มาก (1-10 วัน) ยังไม่มีข้อมูล
  retention พอจะประเมิน ควรรอดูอีกสักพักก่อนตัดสินใจขยายเพิ่ม

### 7.3 คลังคำถาม
- เติมเคมี difficulty 3 (ตอนนี้ 36 ข้อ = 9% เทียบชีวะ 20%)
- `questions` inactive 423 ข้อฝั่ง junior — **ตัดสินใจแล้ว (15 ส.ค. 2026): ปล่อยไว้ก่อน ยังไม่เปิด**

### 7.4 ของที่ตัดสินใจแล้วว่า "ยังไม่ทำตอนนี้"

| งาน | เหตุผล |

## 9. กฎการทำงาน (ไม่เปลี่ยน)

### 9.1 Workflow
**Survey → Draft → Confirm → Execute → Verify** — ห้ามข้ามเฟส ห้ามแก้โค้ดก่อน survey
หยุดให้ตรวจทีละเฟสสำหรับงานที่แตะ production ไม่รันรวดเดียว

### 9.2 ข้อห้ามเด็ดขาด
- 🔒 **ห้ามแก้** `src/lib/exp.ts` และ `src/lib/evolution.ts`
- **ห้ามให้ AI/agent จัดการ credential** — `supabase link`, DB password, API key กรอกเองในเทอร์มินัล
- **ห้าม apply migration เข้า production โดยไม่มีไฟล์ในrepo คู่กัน**
- **ห้าม log ข้อความ AI ลง `analytics_events`** (ไม่มี validation เนื้อหา) — ใช้ `qmon_messages`
- **มีเด็กจริง 126 คนใช้งานอยู่ (junior 102 / senior 24)** ทุกการแก้ต้องพิสูจน์ว่าไม่กระทบผู้ใช้จริง

### 9.3 บทเรียนที่ต้องจำ (เจ็บมาแล้วทุกข้อ)

| เรื่อง | สิ่งที่ต้องทำ |
|---|---|
| **DB คือ source of truth** | query `information_schema` + `list_migrations` ก่อนเสมอ ไม่เชื่อเอกสารหรือ `schema.sql` |
| **PostgREST ตัดเงียบที่ 1,000 แถว** | ต้อง `.range()` เสมอ หรือทำเป็น SQL function |
| **Race condition ของ counter** | `math_correct`/`science_correct`/`combo_milestones` ต้องผ่าน atomic RPC ไม่ใช่ read-modify-write |
| **Bangkok timezone** | cast `created_at AT TIME ZONE 'Asia/Bangkok'` ก่อน `::date` เสมอ · ห้ามใช้ `current_date` ของ DB (UTC) |
| **`CREATE OR REPLACE FUNCTION` ที่ signature ต่าง** | สร้าง **overload ใหม่** ไม่ใช่แทนที่ → ต้อง `DROP FUNCTION IF EXISTS` ก่อน |
| **Migration timestamp** | MCP gen timestamp ตอน apply ≠ เวลาไทย → ตั้งชื่อไฟล์ตาม version ที่ MCP คืนมา |
| **Next.js 16 canary** | ห้ามรวม `router.push()` + `router.refresh()` → duplicate RSC fetch + UI ค้าง |
| **`track()` จาก server action = no-op เงียบ** | ต้อง insert `analytics_events` ตรง |
| **`balanced` vs `balance`** | DB/type มี d · ชื่อไฟล์รูปไม่มี d · แปลงที่ `petImage.ts` จุดเดียวเท่านั้น |
| **`quiz_attempts.question_id` เป็น bigint** | join กับ `questions.id` ตรงๆ ไม่ต้อง cast |
| **Answer bias** | คำตอบถูกมักยาวกว่าตัวลวง → เกณฑ์ต่างกัน ≤20% + shuffle `correct_index` ก่อน insert |
| **ทดสอบต้องผ่านเบราว์เซอร์จริง** | SQL หรือ `npm run build` ผ่าน **ไม่ใช่หลักฐาน** ว่าฟีเจอร์ทำงาน |
