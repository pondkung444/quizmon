# ระบบ "ประลอง" (PvP) — แผนแบ่งเฟส/สไลซ์

> อิงจาก `claude_pvp-system-design-2026-09-03-draft.md` (design ปิดครบแล้ว)
> ยึด pattern การแบ่งสไลซ์แบบเดียวกับระบบ "ท้าทาย" (raid) v3 §11 + บทเรียนจาก Boss Raid Phase 1
> เอกสารนี้ = แผนงาน ไม่ใช่โค้ด/schema — ยังไม่ลง DB schema/RPC spec จริง (นั่นคือ Survey ของแต่ละสไลซ์)

---

## 0. ตัดสินใจเชิงโครงสร้างก่อนแบ่งสไลซ์

### 0.1 ซ่อนทั้งหมดจนกว่าจะเสร็จ — ใช้ pattern เดียวกับ raid (§11.0)
ไม่ปล่อยระหว่างทาง → schema `pvp_*` เปลี่ยนได้ฟรีจนถึงวันเปิด ไม่ต้องทำ feature flag ซับซ้อน แค่ไม่เปิดปุ่มเมนูล่าง + เช็ค user id ฝั่ง server กันเดา URL (เหมือน raid)

**ข้อยกเว้นที่ต้องระวังเหมือนเดิม:** จุดที่แตะของจริงที่ใช้งานอยู่แล้ว — ในเคสนี้คือ (1) `src/lib/exp.ts` exception และ (2) เมนูล่าง/หน้าสังคมที่ใช้จริงอยู่ (ต้องย้าย "หอเกียรติยศ" ออกจากเมนูล่าง)

### 0.2 อินเตอร์เฟซที่ต้องประกาศตั้งแต่สไลซ์ 1 (แบบเดียวกับ `effectiveStat()`)

ประเด็นคือ PvP อ่านสเตตัสจาก pet ที่ stage 4 (เหมือน raid) แต่ **ไม่มีอุปกรณ์ raid มาบวก** — มีชุดอุปกรณ์ PvP แยกของตัวเอง (ล็อกไว้แล้วว่าแยกชุด) ดังนั้นต้องมีฟังก์ชันของตัวเอง คนละตัวกับ raid's `effectiveStat()`:

```
pvpEffectiveStat(pet, stat)  →  raw + โบนัสจากอุปกรณ์ PvP ที่ equip อยู่ตอนนั้น (loadout ที่ผูกกับแมตช์)
```

สไลซ์ 1 ให้คืน `raw + 0` ไปก่อนได้ (ไม่มีอุปกรณ์ PvP ในสไลซ์ 1) **แต่ทุกจุดที่คำนวณดาเมจ/คริ/SPD ต้องเรียกผ่านฟังก์ชันนี้เท่านั้น** ห้ามอ่าน `pt.stat_*` ตรงๆ — กันสไลซ์ถัดไป (อุปกรณ์ PvP) ต้องรื้อ

จุดที่สองที่ต้องประกาศ interface ล่วงหน้า: **โครงสร้างการ์ด**
```
PvpCard = { chapter_id, subject, difficulty, effect_id | null, question_id (จั่วตอนใช้จริง ไม่ใช่ตอนสร้างมือการ์ด) }
```
ล็อกรูปร่างนี้ตั้งแต่สไลซ์ 1 (แม้สไลซ์ 1 จะ implement แค่การ์ดเปล่า ไม่มี `effect_id`) เพราะสไลซ์ 2 (เอฟเฟกต์การ์ด) แค่เติมค่าใน field ที่มีอยู่แล้ว ไม่ต้องรื้อ schema การ์ด

### 0.3 namespace
ใช้ `pvp_*` (`pvp_matches`, `pvp_rounds`/`pvp_cards`, `pvp_tickets`, `pvp_equipment` ฯลฯ) — คนละก้อนกับ `raid_*` และ `boss_raid_*` ทั้งหมด ห้ามชนกับทั้งสองระบบ

### 0.4 ทำไมลูปมาก่อน (เหมือน raid, ย้ำเหตุผล)
เอฟเฟกต์การ์ด/อุปกรณ์ PvP/ตั๋ว เป็น "ของที่ประดับบนลูปที่เล่นจบได้" ถ้าสร้างก่อนลูป จะทดสอบไม่ได้จริงในเบราว์เซอร์ (ต้องยัด DB เอง) เกตแบบนั้นไม่ใช่มาตรฐานของโปรเจกต์นี้ — สร้างลูปง่ายที่สุดที่จบแมตช์ได้ก่อนเสมอ

## 1. สไลซ์ 1 — ลูปที่เล่นจบได้ (1 แมตช์แบบง่ายที่สุด)

**ขอบเขต:**
- Schema: `pvp_matches` (สถานะแมตช์, ผู้ท้า/ผู้รับ, pet+loadout ที่เลือก, ยกปัจจุบัน, เลือดสองฝั่ง, ผลลัพธ์), `pvp_challenges` (คำท้าค้าง ก่อนตอบรับ)
- ท้า → เลือก Qmon (stage 4, ต้อง junior/junior หรือ senior/senior เท่านั้น) → ส่งคำท้า → เพื่อนกดรับ → เลือก Qmon ฝั่งตัวเอง → เข้าแมตช์ทันที (ไม่มี lobby)
- ปฏิเสธคำท้า → แจ้งผู้ท้า
- โครงสร้างยก: ping-pong ตัดสินด้วย SPD ว่าใครส่งก่อน (ผ่าน `pvpEffectiveStat` ตาม §0.2)
- จั่วการ์ด **เปล่า** (ไม่มีเอฟเฟกต์ — `effect_id = null` ทุกใบในสไลซ์นี้) เอียงตาม lane ของ Qmon ที่เลือก, จากทุกบทที่มีข้อสอบ ≥1 ข้อ, กันจั่วซ้ำภายในแมตช์เดียวกัน
- ตอบคำถาม → ตอบถูก = ไม่โดนดาเมจ, ตอบผิด = โดนดาเมจฐานตาม ATK/DEF (เลขจริงยังไม่จูน — ใช้เลขคร่าวๆ ชั่วคราวเพื่อให้ลูปเดินได้ แล้ว flag ว่าต้องจูนทีหลัง)
- ตัวจับเวลา 60 วิ/ยก (SPD ให้วินาทีเพิ่ม — สูตรจริงรอจูนเหมือนดาเมจ)
- เพดาน 30 ยก → ตัดสินด้วยเลือดคงเหลือ
- จบแมตช์ → หน้าจอชนะ/แพ้ (โทนตามที่ล็อก: แพ้ไม่พูดคำว่าแพ้, ชนะไม่ gloat) → บันทึกผล
- Timeout ระหว่างเล่น 3 วัน → ทิ้งแมตช์ ไม่มีผู้ชนะ ไม่กระทบสถิติ
- Timeout คำท้าค้าง 24 ชม. → หมดอายุอัตโนมัติ
- จำกัดคำท้าค้าง 3-5 ใบ/คน (เลือกเลขจริงตอน Draft สไลซ์นี้)
- EXP: `source='pvp'` ให้ EXP จริงจากการตอบทุกข้อ **แต่ยังไม่ต้องขอ exception soft-cap ในสไลซ์นี้** — ปล่อยให้ตันที่ 180 ไปก่อนได้ชั่วคราว (ตั๋วยังไม่มีในสไลซ์นี้ ปริมาณเล่นจะต่ำอยู่แล้ว ไม่กระทบการทดสอบลูป) → ย้าย exception จริงไปทำท้ายสไลซ์ 3 (ตั๋ว) ตามหลัก "แตะไฟล์ protected ทำท้ายสุดของเฟสที่เกี่ยวข้อง"
- ไม่มีตั๋วในสไลซ์นี้ — ท้าได้ไม่จำกัด (ตั๋วเป็นสไลซ์ 3)
- ไม่มีอุปกรณ์ PvP จริง — `pvpEffectiveStat` คืน raw ตรงๆ

**งาน DB/RPC (แยกจาก UI):**
- Migration: `pvp_challenges`, `pvp_matches`, ฟังก์ชัน RPC เช่น `create_pvp_challenge()`, `accept_pvp_challenge()`, `submit_pvp_card()`, `resolve_pvp_round()`
- `pvpEffectiveStat()` ประกาศ interface (คืน raw+0)
- Junior/Senior guard ฝั่ง server (เช็ค `grade_band` ไม่ใช่ `subject` — เรียนรู้จาก raid ว่า senior physics เก็บเป็น `subject='math'`)

**งาน UI (แยกจาก DB/RPC):**
- หน้าท้า/เลือก Qmon+loadout (blind — ไม่เห็นของอีกฝ่าย)
- หน้าดวล (การ์ด 5 ใบ, จับเวลา, ผลยก)
- หน้าจอจบแมตช์ (ชนะ/แพ้ โทนบวก)
- ยังไม่ต้องทำเมนูล่าง/entry point เต็มรูปแบบ — เข้าถึงผ่าน URL ตรงพอสำหรับเทส (เหมือน raid สไลซ์ 1 ที่ยังไม่ทำ entry สวยงาม)

**เกตผ่าน (เล่นเองแล้วมั่นใจว่าไม่ต้องรื้อ):**
- ท้า → รับ → เลือก Qmon สองฝั่ง → ดวลจบ 1 แมตช์ครบในเบราว์เซอร์จริง ระหว่างบัญชีทดสอบ 2 บัญชี (ใช้ `panuwat.pond@gmail.com` / `daou@mail.com` — **ห้ามใช้บัญชีนักเรียนจริง**)
- ปิดแอปกลางแมตช์แล้วกลับมาต่อได้ (resume กลางยก — เช็คว่า async ทำงานจริง ไม่ใช่แค่ demo แบบเปิดสองแท็บพร้อมกัน)
- Junior ท้า senior ไม่ได้ (ทดสอบจริง ไม่ใช่แค่อ่านโค้ด)
- Timeout ทั้งสองแบบ (คำท้าค้าง 24ชม., ระหว่างเล่น 3 วัน) — ทดสอบผ่านการปรับ timestamp ใน DB ตรงๆ เพื่อจำลอง ไม่ต้องรอเวลาจริง

**หยุดถามปอนด์ก่อนไปต่อ:**
- เลขดาเมจฐาน/timer ชั่วคราวที่ใช้เดินลูป (จะยังไม่ใช่เลขจูนจริง — ต้องขอ sign-off ว่า "ใช้ไปก่อนได้ ไม่ใช่เลขสุดท้าย" กันปอนด์เข้าใจผิดว่านี่คือเลขจูนแล้ว)
- จำนวนคำท้าค้างสูงสุด (3 หรือ 5?)
- ชื่อ RPC/ตาราง `pvp_*` ที่ตั้งไว้ (confirm namespace ก่อน apply migration)

## 2. สไลซ์ 2 — เอฟเฟกต์การ์ด

**ขอบเขต:**
- เติม `effect_id` ให้การ์ดจริง 6 แบบ (สวนกลับ/เจาะเกราะ/ฮีลเมื่อสำเร็จ/เดิมพันสูง/เร่งเวลา/ดูดเลือด) + สัดส่วน ~40% การ์ดเปล่า
- Logic คำนวณผลของแต่ละเอฟเฟกต์ตอน resolve ยก (ทุกจุดต้องผ่าน `pvpEffectiveStat` เดิม ไม่รื้อ)
- เอฟเฟกต์ "เร่งเวลา" แก้ timer per-round (ใช้ค่าฐาน 60 ที่ประกาศไว้แล้วในสไลซ์ 1)

**งาน DB/RPC:** เพิ่มคอลัมน์/ตาราง `pvp_card_effects` (definition), เติม logic ใน `resolve_pvp_round()` ที่มีอยู่แล้ว — ไม่สร้าง RPC ใหม่ทั้งชุด แค่ต่อของเดิม

**งาน UI:** แสดงไอคอน/ป้ายเอฟเฟกต์บนการ์ด, ข้อความอธิบายสั้นๆ ตอนเลือกการ์ด

**เกตผ่าน:** เล่นแมตช์จริงแล้วเจอเอฟเฟกต์ทั้ง 6 แบบทำงานถูกต้องอย่างน้อยคนละ 1 ครั้ง (สุ่มบังคับให้ขึ้นครบระหว่างเทส ไม่ต้องรอสุ่มธรรมชาติ) — ตรวจว่าดาเมจ/เลือด/timer เปลี่ยนตามที่ออกแบบจริง ไม่ใช่แค่ข้อความขึ้น

**หยุดถามปอนด์:**
- ถ้าเทสแล้วเอฟเฟกต์ไหนรู้สึกแรง/อ่อนเกินไปเมื่อเจอของจริง (ตัวเลขยังไม่จูน — คาดว่าจะมีรอบปรับ)

## 3. สไลซ์ 3 — ตั๋วเข้าเล่น + EXP exception

**ขอบเขต:**
- ตาราง `pvp_tickets` (คงเหลือ, เพดาน 15)
- แจกฟรี 2 ใบ/วัน (cron หรือ lazy-grant ตอน login — ตัดสินใจตอน Draft)
- +1 ใบ เมื่อลง raid จบ 1 รอบ — **จุดนี้แตะฟีเจอร์ raid ที่ใช้งานจริงอยู่แล้ว ทำเป็นขั้นตอนแยก ระวังเป็นพิเศษ** (บทเรียนจาก raid: ท่อตั๋วต่อกับเคลมผจญภัยต้องทำท้ายสุดของสไลซ์ที่เกี่ยวข้อง)
- หักตั๋วจากผู้ท้าตอนส่งคำท้า, คืนตั๋วถ้าปฏิเสธ/timeout ก่อนเริ่ม
- **ขอ exception `src/lib/exp.ts` ณ จุดนี้** — เติมเงื่อนไข `if (source === 'pvp') skip soft-cap check` จุดเดียวใน `calculateExpForAnswer()` ตามที่ล็อกไว้ในเอกสาร (ทำเป็นขั้นตอนสุดท้ายของสไลซ์นี้ เพราะแตะไฟล์ protected)

**งาน DB/RPC:** `pvp_tickets` + trigger/RPC หักคืนตั๋ว, hook เข้า raid completion (จุดเดียว, แคบที่สุดเท่าที่ทำได้), diff `calculateExpForAnswer()` ปัจจุบันกับ Claude Code ก่อนแก้จริง (เหมือนทุกครั้งที่ผ่านมา ไฟล์ที่ร่างมักไม่ตรง 100% กับ base ล่าสุด)

**งาน UI:** แสดงจำนวนตั๋วคงเหลือ, disable ปุ่มท้าเมื่อตั๋วหมด, ข้อความอธิบายวิธีได้ตั๋วเพิ่ม

**เกตผ่าน:**
- ตั๋วหัก/คืนถูกต้องตามเคสทั้งหมด (ท้าสำเร็จ / ปฏิเสธ / timeout) ทดสอบจริงในเบราว์เซอร์
- ลง raid จบ 1 รอบจริง → เช็คว่าตั๋ว PvP ขึ้น +1 จริง โดย **raid เดิมไม่พังหรือมีพฤติกรรมเปลี่ยน** (regression check บน raid ด้วย ไม่ใช่แค่เช็ค PvP)
- เล่น PvP เกิน 180 EXP/วันได้จริงโดยโหมดอื่น (topic_select, ท้าทาย ฯลฯ) ยังตันที่ 180 ตามปกติ — แยกกันจริง

**หยุดถามปอนด์ก่อนแตะ `exp.ts`:** ให้ยืนยัน diff ที่จะแก้แบบเห็นโค้ดจริงก่อน apply (ไม่ใช่แค่คำอธิบาย) เพราะเป็นไฟล์ protected ที่แก้ได้เฉพาะ exception ที่ระบุไว้เท่านั้น

## 4. สไลซ์ 4 — อุปกรณ์ PvP

**ขอบเขต:**
- ชุดอุปกรณ์ PvP แยกต่างหาก (ไม่ใช้ร่วมกับ raid) — เลือกก่อนดวล, ล็อกตอนอยู่ในแมตช์
- เติม `pvpEffectiveStat()` จาก `raw+0` → `raw + โบนัสอุปกรณ์ PvP` (จุดเดียว ตามที่ประกาศ interface ไว้ตั้งแต่สไลซ์ 1)

**งาน DB/RPC:** `pvp_equipment_items`, equip/unequip RPC, งบแต้ม/สเกลอุปกรณ์ (เลขจริงรอ Draft — จะอ้างอิง pattern งบ 75 แต้มของ raid หรือคิดใหม่ ต้องคุยกับปอนด์)

**งาน UI:** หน้าเลือกอุปกรณ์ก่อนดวล (blind, ไม่เห็นของอีกฝ่ายจนเปิดแมตช์)

**เกตผ่าน:** ใส่อุปกรณ์แล้วดาเมจ/เลือดในแมตช์จริงเปลี่ยนตามสูตร ถอดออกแล้วกลับเป็นค่า raw เดิม

**หยุดถามปอนด์:** งบแต้มอุปกรณ์ PvP (ใช้ 75 เหมือน raid หรือเลขใหม่?) — ไม่มีมติล็อกในเอกสาร design ต้องเคาะก่อนเริ่มสไลซ์นี้

## 5. สไลซ์ 5 — ทางเข้า, เมนูล่าง, สถิติ, Push

**ขอบเขต:**
- เปลี่ยนเมนูล่าง 4 ปุ่ม: บ้าน/สังคม/ฟาร์ม/**ประลอง** (เอา "หอเกียรติยศ" ออก)
- ย้ายหอเกียรติยศไปเป็นลิงก์ในแท็บ "อันดับ" ของหน้าสังคม (ไม่เพิ่มแท็บที่ 4 — เคารพกฎ 3 แท็บที่ล็อกไว้)
- หน้าหลัก "ประลอง": กลุ่ม "ถึงตาคุณ" ขึ้นก่อน + ส่วนอื่นซ้อนล่าง
- Badge ตัวเลขแดงที่ปุ่มเมนูล่าง (นับรวม "ถึงตาคุณ" + คำท้าใหม่ที่ยังไม่ตอบรับ/ปฏิเสธ)
- Push: คำท้าใหม่ ✅, ถึงตาคุณ ✅, ผลจบแมตช์ ❌ (ไม่ส่ง)
- สถิติหน้าโปรไฟล์: จำนวนชนะ/เสมอ PvP (ไม่มี leaderboard แยก)

**งาน DB/RPC:** view/count สำหรับ badge, hook push notification เข้าระบบ push ที่มีอยู่แล้ว (เหมือน raid — ต่อ event-driven push type ใหม่ ไม่สร้างระบบ push ใหม่)

**งาน UI:** เมนูล่าง (แตะของที่ใช้จริง — ระวัง regression หน้าสังคม/บ้าน/ฟาร์มเดิม), หน้าโปรไฟล์เพิ่มสถิติ

**⚠️ จุดที่ต้องระวังเป็นพิเศษ:** สไลซ์นี้แตะเมนูล่าง+หน้าสังคมที่นักเรียนใช้งานจริงอยู่แล้ว (178+ accounts) ต่างจากสไลซ์ 1-4 ที่เป็นหน้าใหม่ทั้งหมด → **ต้องเทส regression เต็มของเมนูล่าง/หน้าสังคมเดิมก่อนถือว่าผ่าน** ไม่ใช่แค่เทสฟีเจอร์ใหม่

**เกตผ่าน:**
- เมนูล่างใหม่ใช้งานได้ครบ 4 ปุ่ม, หอเกียรติยศเข้าถึงได้จากแท็บอันดับ
- Push 2 ชนิดที่ต้องส่งจริง verify บน Android จริง (ตาม pattern เดิมของโปรเจกต์ที่ต้อง verify push บน device จริง ไม่ใช่แค่ log)
- Regression: หน้าสังคม/บ้าน/ฟาร์มเดิมไม่พัง

**หยุดถามปอนด์:** ยืนยันก่อน merge ว่าจะเปิดปุ่มเมนูล่างให้ใครเห็นก่อน (ทดสอบกับนักเรียนจริงกี่คนก่อนเปิดทั้งห้อง — ตาม pattern เกตสุดท้ายของ raid §11.2)

## 6. ลำดับสไลซ์ + จุดพึ่งพา

```
สไลซ์ 1 (ลูปเปล่า) ─┬─→ สไลซ์ 2 (เอฟเฟกต์การ์ด)
                     ├─→ สไลซ์ 3 (ตั๋ว + exp.ts exception)  ← แตะ raid completion, ต้องทำหลังสไลซ์ 1 นิ่งแล้ว
                     └─→ สไลซ์ 4 (อุปกรณ์ PvP)
สไลซ์ 2,3,4 ทำคู่ขนานกันได้ (ไม่ผูกกัน) แต่ทั้งหมดต้องเสร็จก่อนสไลซ์ 5
สไลซ์ 5 (เมนูล่าง/entry) ← ทำท้ายสุดเสมอ เพราะเป็นจุดเดียวที่ "เปิดสวิตช์" ให้นักเรียนเห็น
```

**เกตสุดท้ายก่อนเปิดจริง (เพิ่มจาก 5 สไลซ์ข้างบน):** ให้นักเรียน 2-3 คู่ (junior คู่หนึ่ง senior คู่หนึ่ง) ลองท้ากันจริงก่อนเปิดทั้งห้อง — เพื่อดูว่า async/ping-pong เข้าใจง่ายไหม, เอฟเฟกต์การ์ดสื่อสารชัดไหม, timer 60 วิ กดดันเกินไปไหม (ทดสอบเองไม่ได้เพราะต้องมีคู่จริง 2 ฝั่ง)

## 7. สรุปจุดที่ต้องหยุดถามปอนด์ (รวมทุกสไลซ์)

| สไลซ์ | จุดที่ต้องถามก่อนไปต่อ |
|---|---|
| 1 | เลขดาเมจ/timer ชั่วคราว (sign-off ว่าไม่ใช่เลขจูนจริง), จำนวนคำท้าค้างสูงสุด, ชื่อ namespace `pvp_*` |
| 2 | ความแรงของเอฟเฟกต์หลังเจอของจริง (คาดว่าต้องปรับ) |
| 3 | Diff โค้ดจริงก่อนแตะ `exp.ts` |
| 4 | งบแต้มอุปกรณ์ PvP (ไม่มีมติล็อกในเอกสาร) |
| 5 | จำนวน/รายชื่อนักเรียนที่ทดสอบก่อนเปิดทั้งห้อง |

## 8. สิ่งที่ยังไม่ทำในเอกสารนี้ (ตั้งใจเว้นไว้)
- DB schema เต็ม (column-by-column) — ทำตอน Draft ของแต่ละสไลซ์ ไม่ใช่ตอนวางแผนเฟส
- เลขจูนจริง (ดาเมจฐาน/% DEF/% คริ) — รอข้อมูลจริงแบบเดียวกับที่เคยทำกับ raid FOC/SPD ห้ามเดาก่อน
- Naming ชื่อเอฟเฟกต์การ์ด/ข้อความ UI สุดท้าย — งาน naming แยกโหมด ทำทีเดียวยาวๆ แบบ raid
