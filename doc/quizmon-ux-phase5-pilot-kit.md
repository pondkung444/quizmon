# เฟส 5 — ชุดทดลองใช้งานจริง

สถานะ: เตรียมทดลอง ไม่ใช่รายงานผลผ่าน และยังไม่เปิด staged rollout

## เป้าหมายและขอบเขต

ทดลองนักเรียน 6–8 คนบนโทรศัพท์จริงผ่าน browser คนละประมาณ 20–30 นาที เลือกเครื่องและขนาดจอหลากหลาย วัดว่าเด็กเริ่มเล่นและเข้าใจสิ่งที่ควรทำต่อได้เองหรือไม่ ไม่เพิ่ม UI เพื่ออธิบายซ้ำโดยไม่มีหลักฐาน

ใช้บัญชีทดสอบแยก ห้ามใช้บัญชีนักเรียนจริง ห้ามบันทึกชื่อจริง อีเมล โรงเรียน รหัสผ่าน คำตอบรายข้อ หรือรหัสเพื่อนในแบบบันทึก ใช้รหัส P01–P08 เท่านั้น ให้ผู้ดูแลจัดเตรียมบัญชีและสิทธิ์การเข้าร่วม/การบันทึกตามนโยบายของโรงเรียน ผู้ทดลองหยุดได้ทุกเมื่อ การถ่ายหน้าจอหรือเสียงต้องได้รับอนุญาตแยก

ผู้ดำเนินการให้ผู้เข้าร่วมใช้เครื่องเอง ไม่บอกชื่อปุ่มหรือเส้นทางก่อนเริ่ม ระหว่างทดลองถามได้ว่า “กำลังมองหาอะไรอยู่” แต่ไม่ชี้นำ บันทึกความช่วยเหลือทุกครั้ง ห้ามนับงานที่มีคนช่วยเป็นสำเร็จเอง

## ก่อนเริ่มแต่ละรอบ

- บันทึกวันที่ browser/อุปกรณ์แบบกว้าง ๆ viewport และ commit/deployment ที่ทดสอบ ห้ามใช้แค่ชื่อ main เพราะเปลี่ยนได้ระหว่างรอบ
- บัญชี A: ผู้เล่นใหม่ มีภารกิจที่ยังไม่ครบและ EXP วันนี้ยังไม่เต็ม
- บัญชี B: Qmon ยังไม่ถึง Stage 4 สำหรับโจทย์ปลดล็อก
- บัญชี C/D: บัญชี UX สำหรับเพิ่มเพื่อนและรับคำขอเท่านั้น
- ผู้ดูแลเตรียมสถานะ food/review และ Stage 4 สำหรับ flow battle ที่เลือก ห้ามแก้สูตร EXP/evolution และห้ามฝืน flow ที่ยังล็อก
- ตรวจเส้นทางด้วย browser ก่อนใช้กับเด็ก: Guest→ไข่→คำถาม, Home, food, review, friend; PvP/Boss ต้องผ่าน flow ที่จะใช้จริงก่อน
- ทดลองระบบด้วยบัญชี QA หนึ่งรอบก่อน ไม่รวมรอบซ้อมในผลเด็ก
- ไม่อ้างว่าเฟส 4 ปิดแล้วจาก SQL/build; การส่ง/รับเพื่อน บล็อก และ PvP/Boss resume/reconnect ต้องมี browser evidence ของตัวเอง

## คำเกริ่นสำหรับผู้เข้าร่วม

“วันนี้เราทดลองว่าเกมใช้ง่ายไหม ไม่ได้ทดสอบว่าเราเก่งแค่ไหน ลองทำตามโจทย์ด้วยตัวเอง ถ้าหาไม่เจอบอกได้ และถ้าอยากหยุดก็หยุดได้เลย”

## โจทย์ทดลอง

อ่านเฉพาะคอลัมน์โจทย์ให้ผู้เข้าร่วมฟัง เกณฑ์และเวลาเป็นของผู้ดำเนินการ ไม่ใช้กดดันเด็ก

| รหัส | โจทย์ที่อ่าน | จุดจบที่บันทึก | จุดสังเกต |
|---|---|---|---|
| T01 | เริ่มเล่นแบบยังไม่สมัคร เลือกไข่ แล้วเริ่มกิจกรรมตอบคำถามครั้งแรก | คำถามแรกแสดง ไม่ต้องตอบถูก | จับจากกดเริ่ม Guest; เป้าหมายมัธยฐานไม่เกิน 180 วินาที |
| T02 | กลับหน้าบ้าน แล้วเลือกสิ่งที่คิดว่าควรทำก่อนวันนี้ | เริ่มภารกิจได้เองในบัญชีที่ภารกิจยังไม่ครบ | ภารกิจมาก่อนฝึก Qmon; ไม่ชี้ชื่อปุ่ม |
| T03 | หลังทำภารกิจ ลองดูว่าวันนี้ Qmon ยังฝึกได้อีกไหม และต้องทำอะไรต่อ | ชี้ progress วันนี้ และอธิบายเป้าหมาย 180 EXP ได้ | ไม่บังคับเก็บเต็ม 180 ในเวลาทดลอง; แยกจาก EXP สะสมและ Stage |
| T04 | ลองเลือกอาหารให้ Qmon แต่ก่อนยืนยันบอกว่าคิดว่าจะเปลี่ยนอะไร | เห็นผลก่อนยืนยัน แล้วทำรายการได้หนึ่งครั้ง | บอกผลต่อบุคลิก/ความก้าวหน้าได้โดยไม่เดา; ไม่ทดสอบรางวัลด้วยการกดซ้ำกับบัญชีจริง |
| T05 | ถ้า Qmon ยังเข้าโหมดนี้ไม่ได้ ลองหาว่าขาดอะไรและจะทำอย่างไร | ระบุ Stage 4 และเส้นทางฝึกจากหน้าที่ล็อก | ไม่ตีความคำตอบจากผู้ดำเนินการว่าเด็กเข้าใจเอง |
| T06 | ดูข้อที่อยากทบทวนหลังจบรอบ แล้วลองเริ่มทบทวน | เปิด review/mini-round ได้ หรือบันทึกว่าไม่มีเส้นทางให้ทำ | ถ้าไม่มีข้อผิด ใช้ fixture ที่เตรียมไว้ ไม่สร้างความผิดโดยแอบแก้คำตอบ |
| T07 | ลองหาเพื่อนในเกมแล้วส่งคำขอ จากนั้นให้เพื่อนรับ | ทั้งคู่เห็นสถานะเพื่อนหลังรับ | ใช้ UX สองบัญชี; ทดลองชื่อเล่นก่อน ลิงก์/QR เป็นทางเลือก; ไม่เปิดเผยรหัสจริงในรายงาน |
| T08 | ลองกลับมาเล่น battle ที่เริ่มไว้หลังออกจากหน้าแล้วเข้าใหม่ | กลับสถานะเกมที่ถูกต้องและเข้าใจว่ารอใคร | เลือก PvP หรือ Boss อย่างน้อยหนึ่ง flow; ไม่สุ่มบังคับใช้โหมดที่ยังไม่ผ่าน QA |

T01–T03 เป็นแกนหลัก ทุกคนทำเหมือนกัน T04–T08 ทำต่อให้ครบเท่าที่เหมาะสม ถ้าหมดเวลาให้ระบุ not_run พร้อมเหตุผล ไม่เติมผลสำเร็จ ไม่มีวัตถุประสงค์ทดสอบคะแนนความรู้

## แบบบันทึกและนิยาม

ใช้ `quizmon-ux-phase5-observations.csv` หนึ่งแถวต่อคนต่อโจทย์ คัดลอกแถวเพิ่มได้

- result: `independent`, `assisted`, `failed`, `not_run`
- time_seconds: เวลาจากอ่านโจทย์จบถึงจุดจบของโจทย์; T01 จับจากกด Guest start ตามนิยาม funnel ระบุเริ่มจับเวลาให้ชัด
- hesitation_count: นับแต่ละช่วงหยุดหาปุ่ม/เส้นทางอย่างน้อย 10 วินาที ไม่รวมเวลาอ่านคำถามหรือเน็ตโหลด
- blocker_code: `navigation`, `copy`, `locked_state`, `network`, `missing_flow`, `other`, หรือว่าง
- notes: พฤติกรรมสั้น ๆ เช่น “กดกิจกรรมอื่นก่อนภารกิจ” ไม่ใส่ PII หรือ transcript ยาว
- help_count: จำนวนครั้งที่บอกเส้นทาง/ปุ่ม; ถ้ามากกว่า 0 ต้องไม่เป็น independent
- สิ่งที่ไม่เห็น/ไม่ได้ทดลองบันทึกว่า unknown/not_run เสมอ

หลังจบรอบถามสั้น ๆ: วันนี้ควรทำอะไรก่อน? EXP วันนี้ต่างจาก EXP สะสมอย่างไร? จุดไหนหายากที่สุด? อยากให้ตัดอะไรออก? เก็บเฉพาะประเด็นไม่ระบุตัวตน

## เกณฑ์สรุปผล

- เป้าหมายที่ล็อกไว้คืออย่างน้อย 6 จาก 8 คนเริ่มกิจกรรมแรกเอง ถ้ามีเพียง 6–7 คนให้รายงานจำนวนจริงและผลชั่วคราว ห้ามอ้างว่าผ่าน 6/8 หรือแปลงอัตราแล้วถือว่าผ่าน gate
- รายงาน first-activity success/time และ Home mission choice แยกกัน; ไม่ใช้ assisted รวมกับ independent
- ค่ามัธยฐาน T01 ใช้เฉพาะเวลาที่จบสำเร็จ พร้อมรายงานจำนวน failed แยก ไม่ให้ failure หายจากรายงาน
- Food/key/ticket/lock: เป้าหมายความเข้าใจ ≥80% เฉพาะโจทย์ที่ทำจริง พร้อมระบุจำนวนตัวอย่าง ไม่สรุป ticket/key จาก food อย่างเดียว
- ห้ามปิด pilot ถ้ามี P0/P1 ด้านข้อมูลหาย รางวัลซ้ำ เข้าเล่นไม่ได้ หรือบัญชี/สิทธิ์รั่ว
- ก่อนตัดสิน scale ใช้ baseline และหลังเปลี่ยนบนช่วงเวลา กลุ่มสถานะ และ deployment ที่เทียบกันได้ ไม่เหมาว่าผลดีจากผู้ทดลองจำนวนน้อยคือผล causal

## Analytics และ rollout gate

ตรวจการส่ง event ที่ใช้งานจริงก่อนอ่านตัวเลข `guest_ready`, `home_next_action_viewed`, `activity_started`, `activity_completed`, `reward_claimed`, `review_opened` ตาม contract เดิม ไม่มี event ให้ระบุ missing instrumentation ไม่เติมตัวเลขจากความจำ

ไม่ลบ test account/session ด้วยสคริปต์อัตโนมัติในชุดนี้ ให้ผู้ดูแลแยกและนำ QA/pilot/test sessions ออกจากชุด baseline จริงตามนโยบาย พร้อมยืนยันรายงาน exclusion ก่อนใช้ metric โดยไม่ลบข้อมูลผู้เล่นจริง

การเปิด 10%→50%→100% ยังไม่ implement หรือเปิดใช้: ต้องระบุฟีเจอร์ที่ยังไม่ได้เปิดจริง ให้คง cohort แบบ deterministic มี kill switch กลับพฤติกรรมเดิม และมี baseline/เกณฑ์ error/ช่วงสังเกตที่เจ้าของผลิตภัณฑ์อนุมัติก่อน ห้ามอ้างว่า UX ที่ขึ้น main ไปแล้วทั้งหมดอยู่ใน cohort 10% และห้ามลด/ซ่อนฟีเจอร์เดิมโดยพลการ

แต่ละขั้นต้องมี browser smoke, ไม่มี duplicate reward/submission, ไม่มี P0/P1, metric activation/completion ไม่ถอยตามเกณฑ์ที่ตกลง ถ้าตัวอย่างไม่พอให้คงขั้นเดิม ไม่ขยายอัตโนมัติ หากรางวัล/สิทธิ์ผิดหยุดทันทีและใช้ kill switch ของฟีเจอร์ที่ระบุ

## สิ่งที่ต้องให้เจ้าของผลิตภัณฑ์จัดเตรียม

ผู้เข้าร่วม 6–8 คน เวลา/ผู้ดำเนินการทดลอง โทรศัพท์จริง บัญชี UX ที่ผู้ดูแลเตรียม และการอนุญาตที่เหมาะสม ก่อนเก็บข้อมูลจริง ส่วนนี้ agent ทำแทนการทดลองกับเด็กจริงไม่ได้

ผลส่งมอบถัดไป: ตารางผลจริง → จัดระดับปัญหา → ข้อเสนอ scale/iterate/simplify → backlog จากหลักฐาน ไม่ใช่เพิ่ม UI ตามความรู้สึก
